[[section-concepts]]
== Cross-cutting Concepts


ifdef::arc42help[]
[role="arc42help"]
****
.Content
This section describes crosscutting concepts (practices, patterns, regulations or solution ideas).
Such concepts are often related to multiple building blocks. 
They may include many different topics, such as the topics shown in the following diagram:

image::08-concepts-EN.drawio.png["Possible topics for crosscutting concepts"]

.Motivation
Concepts form the basis for _conceptual integrity_ (consistency, homogeneity) of the architecture. 
Thus, they are an important contribution to achieve inner qualities of your system.

This is the place in the template that we provided for a cohesive specification of such concepts.

Many of these concepts relate to or influence several of your building blocks. 

.Form
The form can be varied:

* concept papers with any kind of structure
* example implementations,especially for technical concepts
* cross-cutting model excerpts or scenarios using notations of the architecture views

.Structure
Pick **only** the most-needed topics for your system and assign each a level-2 heading in this section (e.g. 8.1, 8.2 etc).

DO NOT ATTEMPT to cover all of the topics of the aforementioned diagram.


.Further Information

Some topics within systems often concern multiple building blocks, hardware elements or development processes.
It might be easier to communicate or document such _cross-cutting_ topics at a central location, instead of repeating them in the description of the concerned building blocks, hardware elements or development processes.

Certain concepts might concern **all** elements of a system, others might only be relevant for a few.
In the diagram above, logging concerns all three components, whereas security is relevant only for two components.


See https://docs.arc42.org/section-8/[Concepts] in the arc42 documentation.
****

=== Identity

[cols="1,3",options="header"]
|===
|Record |How the importer finds it again
|Cloud |IONOS provider organization (`provider_id`) and VDC UUID (`provider_resource_id`). Resolution also checks the configured customer.
|LAN, NAT gateway or load balancer |Parent `cloud_id` and local `provider_resource_id`, within each class.
|VPN gateway |`org_id`, `source_namespace` and `provider_resource_id`. An example `source_namespace` value is `IONOS VPN - org 7 - provider 3 - contract 42 - de-txl/ipsec`. It includes the configured customer, provider, optional contract, region and protocol. The required `cloud_id` places the gateway. The importer rejects a change of owning VDC for that identity.
|VPN LAN attachment |Gateway and resolved Cloud LAN. Every connection must resolve inside one observed VDC, even when another Cloud has a LAN with the same number.
|VPN address assignment |Owning LAN attachment or WireGuard interface's gateway, plus canonical host literal (Bare) or IP object key (Bridge). The reported prefix is a mutable field.
|===

=== Ownership

The VDC and LAN sources own mapped inventory fields. An imported Cloud retains its CMDB lifecycle and business criticality.
For REST-managed topology, `ionos_source_key` identifies rows created by this source. A matching manual or foreign row keeps its ownership. In bridge mode `ionos_synced_ip_id` remembers the last imported address key so a manual change of reference is detectable.
On confirmed withdrawal the writer removes eligible source-owned assignments first. A remaining child protects its parent, and removing an assignment keeps the shared TeemIP host.
The independent `source_key` on a Cloud-to-block/subnet link serves the ownership rule described in <<section-building-block-view,the building block view>>. https://github.com/rudnerbjoern/iTop-br-ionos-cloud-collector/blob/fc97fb65ad334e506c1121193965fb27e16c4a60/collectors/src/InventoryReconciler.php[Ownership checks and child-first removal]

[[inventory-coverage]]
=== Completeness

Coverage belongs to a selected product, API base, collection and, for nested Compute lists, parent. A complete list with zero items is evidence of absence only in that scope. A denied or missing page is incomplete, even when earlier pages returned items.
Incomplete required Compute coverage stops synchronization before the parent writers. A complete empty Cloud or LAN source retains existing CIs under its deletion policy. For NAT and load balancers, a complete child list can withdraw owned rows within its observed VDC.

For VPN the withdrawal boundary is one selected *region and protocol* within the configured customer/provider/contract source.
A failed page or invalid VDC/LAN reference prevents the writer from applying that list. Other complete regional protocol lists can reconcile.
