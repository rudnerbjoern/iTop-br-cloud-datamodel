[[section-runtime-view]]
== Runtime View


ifdef::arc42help[]
[role="arc42help"]
****
.Contents
The runtime view describes concrete behavior and interactions of the system’s building blocks in form of scenarios from the following areas:

* important use cases or features: how do building blocks execute them?
* interactions at critical external interfaces: how do building blocks cooperate with users and neighboring systems?
* operation and administration: launch, start-up, stop
* error and exception scenarios

Remark: The main criterion for the choice of possible scenarios (sequences, workflows) is their *architectural relevance*. It is *not* important to describe a large number of scenarios. You should rather document a representative selection.

.Motivation
You should understand how (instances of) building blocks of your system perform their job and communicate at runtime.
You will mainly capture scenarios in your documentation to communicate your architecture to stakeholders that are less willing or able to read and understand the static models (building block view, deployment view).

.Form
There are many notations for describing scenarios, e.g.

* numbered list of steps (in natural language)
* activity diagrams or flow charts
* sequence diagrams
* BPMN or EPCs (event process chains)
* state machines
* ...


.Further Information

See https://docs.arc42.org/section-6/[Runtime View] in the arc42 documentation.

[[vm-reservation-flow]]
=== From a reservation to a running server

. An administrator reserves a native `VirtualMachine` in the customer's Cloud. A logical interface already references that CI. A second Cloud can have the same display name and a VM of the same name.
. The collector reads every page of each VDC's server list. After Cloud synchronization, it resolves the provider's VDC ID to an iTop Cloud and verifies its customer. That Cloud supplies both the VM's host and its organization.
. On the first observation the server has no matching provider identity. The collector checks the reservations and all incoming claims for that Cloud. A single eligible reservation gives the VM synchronization source an existing iTop ID. The source records the provider identity and updates the same CI. With no eligible reservation, the collector creates an identified VM and passes its ID to the same source.
. Open the Cloud's *Virtual machines* list. The VM shows its IONOS server type and, for a server reporting four cores and 2048 MB, native CPU `4` and RAM `2048 MB`. After a source rename, the list shows the new name on the original CI. Its logical interface still points to that ID. A later observation that omits either metric preserves its stored value.

If page two fails, page one cannot authorize an adoption or an update in that VDC. Other complete VDC lists can still be processed. The run reports the failed scope. A complete empty list leaves both reservations and previously imported VMs in place. https://github.com/rudnerbjoern/iTop-br-ionos-cloud-collector/blob/a20bf4e361aaa1519e8c63db88b80e329e923cbf/tests/vm-import.php[Installed-target VM scenarios]

[[vpn-partial]]
=== IPsec page two fails while WireGuard completes

With page size one, page one contains a proposed IPsec rename. Page two returns HTTP 403. The reader retains partial evidence, and `VpnSync::apply` checks completeness *before* calling the writer for <<inventory-coverage,that region and protocol>>.
The log contains `de-txl/ipsec` and the literal text `1 pages read`. IPsec keeps the name set by the preceding successful import, `Fixture IPsec renamed`. The incomplete list authorizes no withdrawal.
The complete WireGuard list updates its gateway to `WireGuard after page failure`. After processing the independent lists, the collector raises an error and Base exits unsuccessfully.
The VPN fixture calls `runCollector($dir, false)` for this 403 response. The shared fixture helper checks that the Base process returned a nonzero status. https://github.com/rudnerbjoern/iTop-br-ionos-cloud-collector/blob/fc97fb65ad334e506c1121193965fb27e16c4a60/tests/vpn-import.php#L164-L177[VPN fixture call and record assertions] · https://github.com/rudnerbjoern/iTop-br-ionos-cloud-collector/blob/fc97fb65ad334e506c1121193965fb27e16c4a60/tests/vdc-sync.php#L77-L86[Shared exit-status assertion]

The old IPsec state survives because the collector skips that list before writing it. A failure during REST writes has different consequences (<<section-technical-risks,risks>>). https://github.com/rudnerbjoern/iTop-br-ionos-cloud-collector/blob/fc97fb65ad334e506c1121193965fb27e16c4a60/collectors/src/VpnSync.php#L33-L50[Per-list failure handling]

A gateway reports public host `203.0.113.48` and `192.0.2.49/27` on LAN 17. NatInventory separates the private host and prefix. [[allocation-flow]]
=== VDC IPv6 allocation and manual IPAM links

With the bridge and IPv6 Management installed, a VDC reports `2001:db8:4200:100::/56`. Before staging Clouds, VdcSync resolves both boundaries to one existing customer IPv6Block. An omitted allocation, invalid prefix or unresolved block stops the run here. After the Cloud exists, CloudIpLinkSync reads its individual links. A manual link to that exact block satisfies the observation and stays manual on repeat import. For a replacement allocation the writer establishes and confirms the new pair before deleting an old link owned by this source. An explicit null releases only that source's previous link on the observed Cloud. An unconfirmed creation retains the old link; a failed deletion can leave both until retry. The block and unrelated subnet links survive. On Bare the allocation can still appear in the local report. https://github.com/rudnerbjoern/iTop-br-ionos-cloud-collector/blob/34b9dc6ff8906b6e14bc38fef1ae363cb86f4e4e/collectors/src/CloudIpLinkSync.php[Association writer] · https://github.com/rudnerbjoern/iTop-br-ionos-cloud-collector/blob/34b9dc6ff8906b6e14bc38fef1ae363cb86f4e4e/tests/Unit/CloudIpLinkSyncTest.php[Manual match and failed writes]
